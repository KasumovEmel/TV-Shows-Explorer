# Design

## Context

Аудит исходников относительно [правил VIPER](../../../.agents/rules/architecture.md). Пути ниже отсчитываются от `src/`.

| Сейчас                                                                                                                                                            | Вывод                                                                                                                                        |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `index.tsx` инициализирует i18n и асинхронно монтирует `App`. В `app/App.tsx` уже есть StrictMode и провайдеры.                                                   | Технический вход и корень приложения на своих местах. Второй компонент в том же файле, `SearchPage`, своего модуля и Presenter не имеет.     |

Действующие спецификации задают пользовательское поведение. Выполненные, но не архивированные изменения уточняют его: `organize-search-results` и `stack-search-results` — переход и список, `centralize-api-errors` — ошибки и кеш, `stabilize-startup-search` — запуск, `unify-header-icon-buttons` — кнопки, `enforce-code-style` — HTTP и проверки. Новая структура заменяет прежнее решение собирать части поиска прямо в `App`; перенос не требует правки или архивации этих изменений.

## Goals / Non-Goals

**Цель:** сценарий можно вызвать с обычными аргументами, проверить его результат без монтирования React и определить по папке, кто им владеет. Источник истины для каждого вида состояния один.

**За рамками:** новые экраны, URL, роутер, редизайн, замена SWR или выбор менеджера состояния для всего приложения. Нумерация страниц выдачи остаётся навигацией внутри одного экрана.

## Decisions

**1. Выделить маршрут и перенести код по владельцам.** Целевое дерево показывает основные узлы; существующие View, стили и ресурсы перемещаются со своими компонентами.

```text
src/app/
├── App.tsx                       # StrictMode, оболочка, слот для children, SearchPage
├── ApiProvider/                  # SWRConfig, включая onError
├── ErrorBoundary/                # включая RecoveryScreen
├── NotificationProvider/         # очередь, Notification и публичный useNotify
├── components/                   # Button, Icon, Brand
└── SearchPage/
    ├── index.ts, SearchPage.tsx, usePresenter.ts, types.ts
    ├── logic/hooks/              # useSearchQuery и useSearchTransition
    ├── Search/                   # SearchField и LanguagePicker
    └── Results/
        ├── logic/                # tasks/, api/, модель Show и преобразования
        └── PagedResults/         # пагинация, карточки и скелетоны
            ├── logic/            # расчёт групп и hooks/ прокрутки
            └── components/       # в том числе общий для двух детей ShowCardLayout
```

У каждого компонента свой `index.ts`, свой `usePresenter.ts` при наличии логики. Статической раскладке карточки пустой хук не нужен. Родитель передаёт дочерним блокам данные и обработчики через пропсы; дети не импортируют родительский компонент или соседнюю ветку. Для внутренних типов и функций используй модуль их общего владельца. Один файл категории остаётся прямо в `logic/`, второй создаёт подпапку. Не заводить общие `app/tasks/` или `app/api/` для единственного маршрута.

**2. Хранить состояние поиска у его владельца.** Presenter маршрута `SearchPage` использует `useSearchQuery` для текста поля и подтверждённого запроса. При изменении нормализованного текста он сразу сбрасывает подтверждённый запрос. Enter или пауза в 300 мс подтверждают текущую строку. Пробельный ввод возвращает стартовый экран. Маршрут передаёт в `Results` подтверждённый запрос через пропсы.

Presenter `Results` хранит выбранный жанр в локальном состоянии и передаёт его в `filterShows`. Существующий `key={term}` у `Results` сбрасывает выбор при изменении нормализованного текста. При выборе жанра `Results` сбрасывает пагинацию через ключ `PagedResults`, и список открывается с первой группы. При восстановлении экран монтируется с пустым полем. Для этих состояний достаточно React-хуков соответствующих Presenter.

**3. Получать и отбирать сериалы без зависимости от React.** В `Results/logic/tasks/` функция `searchShows(query)` вызывает локальный эндпоинт с обычной строкой и возвращает нормализованные `Show[]`; `filterShows(shows, genre)` возвращает уникальные жанры полной выдачи и подходящие карточки в исходном порядке. Тип `Show` — в `Results/logic/show.ts`, транспортные типы TVmaze — рядом с эндпоинтом. Эндпоинт использует только `@shared/utils/request`. Разбор HTML вынести в утилиту адаптера, а удаление лишних пробелов и сокращение до 160 знаков выполнять чистой функцией.

`Results/usePresenter.ts` передаёт SWR ключ текущего запроса и загрузчик, вызывающий `searchShows(query)`. Ключ `null` приостанавливает загрузку, а ручной повтор вызывает `mutate`. SWR служит единственным кешем ответов TVmaze. Presenter вычисляет карточки из данных текущего ключа и выбранного жанра. Поздний ответ относится к ключу прежнего запроса. Группы по три вычисляет чистая функция у `PagedResults`, используя существующее значение `behavior.pageSize`. Подписи, скролл, распознавание текущей группы и клавиатурный фокус остаются в его Presenter и `logic/hooks/`.

**4. Разделить сценарии оболочки и её интеграции.** Тема применяется на уровне `App`, включая экран восстановления; корневой Presenter вызывает существующий `useTheme`. В `LanguagePicker/logic/changeLanguage.ts` применить язык и сохранить его только при успехе; отделить обычные функции i18next от регистрации React-плагина при запуске. Presenter отвечает за `pending`, подписи и сообщение об ошибке. В `NotificationProvider` выделить правило постановки в очередь и объединения повтора в чистую функцию; React-контекст, таймер и возврат фокуса остаются у их владельцев. Типы событий экспортировать из публичного входа провайдера. HTTP, инициализация i18n, тема, глобальные стили и токены остаются инфраструктурой в `shared`; обратных импортов из неё в `app` нет.

## Risks / Trade-offs

- Смена запроса в полёте или два запуска по Enter и таймеру → сохранить раздельные текст и ключ, проверить список сетевых запросов и запоздалый ответ в `search-request.spec.ts`.
- Изменение порядка провайдеров меняет время жизни кеша и очереди → сохранить `NotificationProvider → ErrorBoundary → ApiProvider → SearchPage` и тестовый `children` внутри `ApiProvider`. Проверить пустой поиск после восстановления и сохранённую выдачу при HTTP 429.
- Перемонтирование поля при анимации теряет фокус и выделение → оставить один экземпляр поля; проверить обычное и уменьшенное движение в `search-transition.spec.ts`.
- Перенос парсера или стилей меняет текст карточки либо размеры скелетона → проверить HTML-сущности, лимит описания, реальные и пустые карточки, мобильную ширину и клавиатурный переход к странице.

## Migration Plan

Сначала зафиксировать результат существующих проверок. После переноса маршрута проверить ввод и фильтр в их Presenter. Затем выделить Tasks поиска и фильтрации, перенести общий UI и оболочку. Проверки для каждого этапа приведены в [задачах](tasks.md).
