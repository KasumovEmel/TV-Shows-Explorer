# Архитектура приложения: VIPER

**Точка входа в приложение — `src/app/App.tsx`.** Здесь собираются провайдеры, бизнес-маршруты и крупные блоки интерфейса. У `src/index.tsx` техническая роль: подготовить окружение и смонтировать `App`. Папки маршрутов и крупных блоков располагай рядом с `App.tsx` и называй по тому, что видит пользователь: например, `SearchPage/` для экрана поиска.

## Ответственность слоёв

- **V — View (`ComponentName.tsx`).** Рисует JSX. Если представлению нужна логика, View вызывает `usePresenter(props)`, отображает полученные данные и привязывает готовые обработчики. Компоненту, который только отображает пропсы, пустой Presenter не нужен.
- **I — Interactor (у нас — Tasks).** Каждая task реализует один бизнес-сценарий как обычная функция TypeScript. Называй функцию и файл по действию: `searchShows` в `searchShows.ts`. Task должна вызываться без рендера компонента: принимает обычные аргументы, может обращаться к API и напрямую читать или изменять Store. Для Redux используй `store.getState()` и `store.dispatch(...)`; для других менеджеров — их API вне UI. Не используй React, хуки, контекст или роутер и не передавай в task полученные из хуков `dispatch` или `navigate`.
- **P — Presenter (`usePresenter.ts`).** Принимает пропсы и готовит данные, флаги и обработчики для View. Здесь живут состояние интерфейса, эффекты, подписки на Store, хуки SWR и работа с платформенным роутером. Обработчик переводит событие UI в аргументы task и при необходимости выполняет переход по её результату.
- **E — Entity (бизнес-сущности и их Store).** Типы описывают сущности предметной области, например сериал; Store хранит их состояние и предоставляет методы работы с ним. Держи Store у владельца сущности. Для небольшого модуля подходит локальный Zustand Store; допустимы также Redux, MobX, Recoil, Effector и другие менеджеры. Выбор библиотеки не меняет границу между task и Presenter.
- **R — Router (бизнес-маршрут).** Маршрут — экран с понятным пользователю назначением, например `SearchPage`. Его папка объединяет части экрана. Чтение параметров и переходы через роутер конкретной платформы выполняет Presenter; отдельный модуль `Router` пока не вводим.

Например, при отправке поиска View привязывает `onSubmit` из Presenter. Presenter извлекает строку из формы и вызывает `searchShows(query)`. Task получает данные через функцию эндпоинта и, если сценарию нужно сохранить результат, вызывает метод Store. Какие карточки отрисовать и куда перейти после выбора сериала, определяет Presenter.

## Папка компонента

Один компонент — одна папка; имя папки и View совпадают и пишутся в PascalCase. В `index.ts` экспортируй компонент и только те типы или функции, которые нужны снаружи. Рядом с View размещай `usePresenter.ts`, `styles.module.css` и при необходимости модульный `store.ts`. Типы публичных пропсов можно оставить рядом в `types.ts`.

Строй дерево по экрану: крупные дочерние блоки клади прямо в папку их владельца. Мелкие компоненты, общие для частей одного экрана, можно собрать в его локальной `components/`. Для нового кода ориентируйся на такую структуру (пример, а не шаблон обязательных файлов):

```text
src/app/
├── App.tsx
├── SearchPage/
│   ├── index.ts
│   ├── SearchPage.tsx
│   ├── usePresenter.ts
│   ├── store.ts
│   ├── SearchField/
│   ├── Results/
│   └── logic/
│       ├── searchShows.ts
│       └── api/
│           ├── fetchShows.ts
│           └── fetchShowDetails.ts
└── components/
    └── Button/
```

## Локальная логика и общий код

Собирай внутреннюю логику компонента в `logic/` по мере необходимости. **Один файл категории лежит прямо в `logic/`; со второго файла той же категории создай подпапку и перенеси туда оба.** Например, единственная task — `logic/searchShows.ts`; после добавления `clearSearch.ts` обе лежат в `logic/tasks/`. Пустые папки не создавай.

| Категория  | Что в ней лежит                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `tasks/`   | Бизнес-сценарии: одна функция с именем-глаголом на файл.                                                                             |
| `hooks/`   | Вспомогательные React-хуки для Presenter. Сам `usePresenter.ts` остаётся рядом с View.                                               |
| `helpers/` | Чистые функции: результат зависит только от аргументов, побочных эффектов нет.                                                       |
| `utils/`   | Служебные функции, которые могут иметь побочные эффекты и вызывать helpers. Как и для helpers, одна функция — один файл с её именем. |
| `api/`     | Функции эндпоинтов, адреса и типы запросов и ответов. Для HTTP вызывай `request<T>()` из `@/app/utils/request`.                      |
| `types/`   | Внутренние типы логики компонента.                                                                                                   |

**Выбирай ближайшего общего владельца по фактическому использованию:**

1. Код нужен одному компоненту — оставь его внутри компонента.
2. Код нужен нескольким компонентам одного маршрута — найди их ближайшего общего родителя. Если фильтр делят два дочерних компонента `Results`, он остаётся в `Results/logic/`; если им пользуются и `SearchField`, и `Results`, его место — `SearchPage/logic/`.
3. Код нужен нескольким компонентам и уже не помещается в один маршрут — вынеси его на уровень маршрутов в `src/app/`. Общие элементы интерфейса и компоненты оболочки (`AppSWRConfig`, `ErrorBoundary`) находятся в `app/components/`. Вспомогательные хуки самого `App` размещай в `app/logic/`, общие технические функции, включая HTTP-клиент, — в `app/utils/`.

Уведомления образуют отдельный модуль `app/notifications/`. Его публичный вход экспортирует `NotificationProvider`, `useNotify` и типы событий. Локализация со словарями находится в `src/i18n/`, глобальные стили и токены — в `src/styles/`.

Импортируй дочерние компоненты через их `index.ts`. Не импортируй внутренности соседней ветки или компонент-родитель. Если двум веткам нужна одна функция, вынеси её к общему владельцу; общий модуль не должен зависеть от компонентов, которые его используют.
