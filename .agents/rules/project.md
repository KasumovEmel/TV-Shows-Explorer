# Правила проекта

- Используй строгий TypeScript в обоих приложениях. Для клиента используй Rsbuild и сохраняй React StrictMode в `apps/web/src/app/App.tsx`.
- На клиенте следуй [правилам VIPER](architecture.md), в API — [правилам серверных модулей](server-architecture.md).
- Используй SWR для кеширования запросов и View Transitions API для переходов между экранами.
- Добавляй тексты интерфейса в английский и русский словари i18next. Английский загружается при запуске, русский — по требованию.
- Обрабатывай общие ошибки API в `AppSWRConfig` через `SWRConfig.onError`. Для HTTP 429 показывай предупреждение о лимите запросов, для остальных ошибок — общее уведомление.
- Общий форматтер, Oxlint и лимит 120 строк применяются к рукописному коду клиента и сервера. Генерируемые файлы проверяются TypeScript и `pnpm api:check`.
- После изменений запусти `pnpm format`, затем `pnpm check`. Исправь оставшиеся ошибки.

## Параметры и типы

- В рукописном JS/TS собственная функция, метод, конструктор или тип колбэка с несколькими входами принимает один объект. Например, `selectGenre({ criteria, genre })`. Объект можно деструктурировать в сигнатуре или в теле. Единственный аргумент можно передавать напрямую.
- Сохраняй позиционную сигнатуру, если её задаёт внешний API: например, `Array.map`, middleware Hono или mutator Orval. Для нестандартного адаптера укажи на месте, какой контракт определяет порядок аргументов. Сгенерированный код не меняй вручную.
- Объявляй интерфейсы, объединения значений, структуры параметров и типы колбэков в `types.ts`, `*.types.ts` или в каталоге `types/` ближайшего владельца. Импортируй их через `import type`. Простые встроенные типы и nullable-ссылки допустимы в аннотациях. Используй вывод типов, когда имя не нужно.
- Oxfmt отвечает за оформление; `pnpm format` и `pnpm check` проверяют эти два соглашения через Oxlint. При изменении сигнатуры обновляй и места её вызова.

## Секреты и чувствительные данные

- Никогда не добавляй в Git и не публикуй на GitHub секреты или другие чувствительные данные, даже временно и даже в приватном репозитории. Это касается файлов, истории и сообщений коммитов, названий веток и тегов, описаний и комментариев в PR и issues.
- К таким данным относятся пароли, токены, приватные ключи, сессионные cookie, персональные данные и параметры доступа к инфраструктуре, включая IP сервера, SSH-хост, пользователя и порт, конфигурацию и порты VPN. В документации, примерах, тестах и скриншотах используй вымышленные значения или имена переменных.
- Передавай чувствительные параметры деплоя через секреты окружения GitHub Actions. Не выводи их в логи, в том числе при отладке и ошибках, и не включай в артефакты сборки или кеш CI/CD.
- Перед коммитом проверь подготовленные изменения, включая новые файлы. Перед push проверь все отправляемые коммиты. Если значение попало в локальный коммит, удали его из всей отправляемой истории до push.
